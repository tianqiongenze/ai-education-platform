Bottleneck Analysis

1. Ingress Rate Limiting RESOLVED

Found: The code-server ingress had limit-rps=30, limit-burst=50, and limit-connections=20. This capped all traffic to 30 requests/second, causing 88.6% of login requests to fail with 503 errors in the initial test.
Fix: Removed all rate limit annotations. Login failures dropped from 88.6% to 0%.

2. CPU-Only LLM Inference UNRESOLVED

Found: No GPU available on either cluster node. All LLM inference runs on CPU via ollama. Chat completions take 30-120 seconds per request on CPU, making 5,000 concurrent chat users impossible.
Required: Minimum 2x NVIDIA A100 (80GB) or 4x A10 GPUs for enterprise-grade LLM serving at this scale.

3. Master Node CPU Saturation MITIGATED

Found: ollama-master consumes ~15 of 16 CPU cores on the master node (96% utilization). This limits scheduling of additional pods on the master.
Mitigation: Reduced CPU requests for code-server (2→500m) and litellm (1→200m) to fit more pods on the worker node.

4. Pod Resource Requests RESOLVED

Found: Original CPU requests (2 CPU per code-server pod, 1 CPU per litellm pod) prevented scaling beyond 5-6 pods due to node capacity.
Fix: Reduced to 500m and 200m respectively, enabling 20 code-server and 11 litellm pods.

Recommendations

Immediate (High Priority)

  1. Add GPU Infrastructure: Deploy minimum 2x NVIDIA A100 (80GB) or 4x A10 GPUs for LLM inference. This is the single most impactful improvement — without GPUs, LLM services cannot meet enterprise concurrency requirements.
  2. Offload ollama-master: Move ollama-master from the control plane node to a dedicated worker to free master node CPU for Kubernetes system components.
  3. Fix Static Asset Paths: Update the load test script to use correct code-server static asset paths for accurate failure rate reporting.

Short-Term (Medium Priority)

  1. Configure HPA: Set up HorizontalPodAutoscaler with proper metrics for code-server and litellm to enable automatic scaling under load.
  2. Implement Smart Rate Limiting: Replace the removed global rate limits with per-user or per-IP rate limiting to prevent abuse while allowing legitimate high-concurrency access.
  3. Connection Pooling: Configure litellm connection pooling for the ollama backend to reduce connection overhead under high concurrency.
  4. Add Node: Add a third worker node to distribute load and provide headroom for scaling.

Long-Term (Strategic)

  1. CDN for Static Assets: Offload code-server static assets (JS, CSS) to a CDN to reduce load on pods and improve response times.
  2. Model Caching: Implement a model response cache (Redis) for frequently requested completions to reduce inference load.
  3. Multi-Region: Deploy in multiple regions for geographic load distribution and disaster recovery.
